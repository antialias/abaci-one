**The rule.** Phase 1w weighs a try 1/2^round right or wrong: first try 1, retry 0.5 / 0.25, counted do-over 1/2^round (the first do-over of a once-wrong item 0.5, was 1.0, §10 P1-9), practice-only 0. Main weighs a wrong try 0, so a wrong answer never lowers pKnown.

**A note on the seeder, read first.** The seeder writes no `masteryWeight`, and BKT reads a missing weight as 1.0, so every seeded wrong answer already counts in full: the seeded students, as the app shows them today, are variant C exactly (checked per skill: 33/33 profiles identical). Their histories were designed (`designSequenceForClassification`) under that full-weight assumption. A real kid's rows are stamped by the server, wrong = 0, so this script stores the seeded answers with main's stamps before reading them back; A is what the same answers mean on main in production, and C is what Phase 1w makes of exactly those stored rows.

**How C is computed.** Through the code as built, not a model of it: the seeded history is stored with main's stamps (wrong 0, correct 1/2^epoch), read back by `getRecentSessionResults`, and passed to `computeBktFromHistory`, whose reader `evidenceWeightOf` re-derives each wrong row's weight from its kind and round. The SQL evidence path (`batchGetRecentBktEvidence`) gives the same BKT state on 33 of 33 profiles. Against the first version of this table, which simulated C by restamping every row with `weightOfTry` and reading the stored weight: identical on all 230 rows (the seeded history holds only first tries, and the simulated sessions' rows are stamped by `weightOfTry` either way).

**The next session (S).** About 15 minutes: 20 first tries dealt round-robin over the profile's seeded skills, linear part. The kid's error rate on a skill is its seeded sequence's error rate (at least 0.05); mistakes are spread through the session by a running sum of those rates, so a strong kid makes one or two and a weak one most. Each mistake is retried: right in round 1 if the skill's seeded accuracy ≥ 0.5, else wrong, then right in round 2 if ≥ 0.25. 32 profiles get a session of 23–58 tries (the brand-new student has no skills to practise). Compare B+S and C+S with A+S, not with A: S moves every variant, and the gate and readiness changes from A to A+S are S, not the rule.

**Does forward-only catch up?** After 5 simulated sessions like S, forward-only and retroactive still classify 9 of 230 rows differently (6 of them strong under forward-only and not under retroactive). Seeded skills on their target: main 148, forward-only 167, retroactive 169 of 230 (after one session: 146, 162, 173; seeded history alone: main 150, retroactive 221).

**What surprised us in BKT.** (1) Main’s rule makes a kid who keeps missing read *strong*: a wrong try adds nothing and each right retry (weight 0.5) adds a little, so 🔴 Multi-Skill Deficient’s `basic.directAddition` (14 of 15 seeded tries wrong) reads 0.777 on main, and 0.965 (strong) after a session with 27 more wrong tries; Phase 1w reads 0.000 after it (0.000 on deploy day). Phase 1w fixes that in both variants. (2) BKT saturates: `bktUpdate` clamps pKnown at 0.999, and from there one wrong answer only takes it to about 0.99, so under forward-only a skill that main’s zero-weight history pinned near 1 needs a run of mistakes to come down. That is why one session of forward-only leaves most inflated developing skills strong, and why it takes a few sessions to catch up. (3) No seeded-strong skill stops being strong under either variant; the moves are developing and weak skills that main reads too high. (4) Already on main, a weight-0 wrong try still counts as an opportunity and lowers the success rate behind BKT confidence (`compute-bkt.ts` increments `opportunities` whatever the weight); only pKnown ignores it.

**Decision: retroactive** (the owner, 2026-11-26, over this table's first recommendation of forward-only; §10 P1w-1). Retroactive is the truer number on day one: weak kids that main reads as strong are corrected before their next session, at the price of the deploy-day jump (75 of 230 rows reclassify before the kid has practised again). Forward-only would have reached nearly the same place within about 5 sessions (9 of 230 rows still differ) and kept the stored weight as the weight. What retroactive costs in the code: one read-time rule, `evidenceWeightOf` (`try-weight.ts`), which every reader of a weight uses (BKT, both evidence paths, the review panel) and the ledger fold must apply too (§6); a correct row keeps its stored weight, so a pre-Phase-1 correct do-over stays 1.0 (its round needs the item's earlier tries, which a row does not hold), and a pre-Phase-1 wrong do-over weighs as round 1.

**Why readiness and the gate do not move.** The linear gate reads only `isCorrect` of first tries, never a weight, so no weighting can flip it (the Y→n changes between A and A+S in the tables are the new session’s mistakes). Readiness needs pKnown ≥ 0.85 *and* the consistency dimension (last 5 correct, ≥ 85 % of the last 15), and a skill that passes consistency sits near pKnown 1 under any of these weightings.
