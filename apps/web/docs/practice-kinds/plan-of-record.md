# Practice kinds: plan of record (2026-11-27, rev. 3)

Companion to the [session architecture plan](../session-architecture/plan-of-record.md) (Phases 1–6 live on prod 2026-11-27, PRs #239–#275) and its [findings](../session-architecture/findings.md). That rework is the foundation: one flow machine owns the rhythm, every write is a CAS on `rowVersion`, one report serves every view, every try has an id, and a part is known to structure only through `PartKind`. This document settles how **many kinds of practice**, each in several **presentations**, plug into that session with no edit outside their own folder.

Paths are under `apps/web/src/`; `L/` is the ledger checkout (`~/projects/soroban-abacus-flashcards-practice/apps/web/`, read-only). Every code claim was re-read at `c12abd87f`. Rev. 2 answers [review 1](review-1.md) (R1–R19), rev. 3 [review 2](review-2.md) (S1–S11); §8 records each finding and what changed. The owner took every §7 recommendation on 2026-11-27; §7 is decisions now.

**The bar.** Adding a kind = one new folder plus one line in each of **three** registries: the shared core registry (`parts/registry.ts`: cursor, judge, presentations, evidence, describe; pure, read on both sides), the server-only planner registry (`parts/planner-registry.ts`: `loadContext`, `offer`, `plan`; S1) and the browser registry (`parts/browser-registry.ts`: views). Rev. 2 said two; the third line is the price of keeping database code out of the client bundle, said plainly (§8 S1). Adding a presentation of an existing kind = one folder plus one line in that kind's presentation list and one in its browser file. Every view (kid's screen, transition, summary, share link and OG, live observer, dashboard lists, adult review, MCP tools, song) handles it with no edit. Tests enforce this (§4 Phase K4). The rhythm `part, (break, part)*, end` then song and summary does not change.

**The rule behind the rule.** A kind that needs an edit outside its folder and its three registry lines is a defect in the architecture, not in the kind; the architecture is fixed first (an entry in §8, then a phase).

## 1. Target model

### 1.1 Taxonomy

| Term | Meaning | Today | Examples to come |
|---|---|---|---|
| **Kind** | What the items are and how the part's cursor moves. Today's behaviour, reproduced exactly: offers come in kind-registration order then the kind's own order (arithmetic: abacus, visualization, linear, as `part-gating.ts:44`); an offer is kept iff `enabled[key]` and `eligible`; `weight` normalized over kept offers (`session-planner.ts:550-553`); minutes = `budget × normalizedWeight`, where `budget = durationMinutes` under `breaks: 'outside'`; `plan()` derives `itemCount = overrideItemsPerPart ?? max(2, floor(minutes·60 / secondsPerItem))` from its own offer (`:594-598` today, arithmetic's pace; R8); no reorder. `maxParts: 3` keeps the break count at today's two (§7 Q2, decided).

**Over the cap: rotation (S5).** When more offers are on and eligible than `maxParts`, `selectOffers` keeps the `maxParts` **least recently practiced** and saves the rest for next time: never practiced sorts first, then oldest `lastPracticedAt`; ties (never-practiced together, or practiced in the same session) break by offer order (kind-registration order then the kind's own order, the same order that already decides part order). Weight is never a tie-break: the adult's weight means minutes, not priority. Kept offers keep their offer order and share the budget by weight as before. The host computes `LastPracticed` from the student's recent plans (`completedAt ?? startedAt` of the latest plan whose `parts[]` has a part with that key and at least one try in it; a pre-K6 part's key is its `type`); the composer is given it, not the DB. With three or fewer chips on, `selectOffers` keeps them all and the plan is today's (golden plan). The saved offers go to `skipped[]` with `reason: 'over-cap'`, so the summary's skipped-parts line reads "Visualize: saved for next time (3 parts per session)" through `skipped-parts.ts` with no new reader. **What the adult sees (K6b):** `/offers` returns the offers, `lastPracticedAt` per key and the policy; the modal runs the same pure `selectOffers` and, when any offer is over the cap, shows under the chips "Today: Abacus, Flash, Linear · Next time: Visualize"; an over-cap chip stays lit with a small "next time" badge, never greyed (it is on, and it will run). The order of "next time" is the rotation's. The tie-break and the rotation are pinned in `compose()`'s unit tests. `NoEligiblePartsError` when nothing is kept (`:546-548`). The trace is stored additively as `summary.composition` (the `summary` JSON column, `session-plans.ts:651`; there is no plan-level generation trace today, `GenerationTrace` is per problem, `:133-146`) and is what the ledger's `plan.decided` event will carry (`L/docs/...:96`).

Why breaks must be in the budget at all: the flow machine runs a break after **every** part transition when breaks are enabled (`session-flow.ts:226-255`), each up to `GameBreakSettings.maxDurationMinutes` (default 5, `session-plans.ts:466-470`); today `durationMinutes` is spent on practice only (`session-planner.ts:595`) and nothing in the planner or the time estimates counts a break minute, so a 12-minute three-part session is 12 + up to 10 minutes and the fixed shape is the only bound. Five parts would make that 12 + 20 (R5).

- **Rows** stay in `session_plans.results` (`session-plans.ts:696`); no column changes in any phase of this plan. New fields on each try are JSON (D8): `itemId`, `outcome`, `answer`, `evidence`, `payload`. `isCorrect` keeps its name and is the server's verdict from K1 on.
- **`evidence`** is `{ skills, presentation }` or `null`. The mode is `masteryModeOf(presentation)` at read time (K2): the kind's `presentations.get(id).masteryMode`, or, for an id no registry knows, the id itself (its own mode: recorded, not consulted). Absent (old rows) → the normalizer derives `{ skills: skillsExercised, presentation: part.type ?? 'linear' }`, reproducing `bktModeOf`'s legacy default (`arithmetic/server.ts:102`, `evidence-query.ts:154`). SQL tells null from absent with `json_type(value, '$.evidence')` (`'null'` vs `NULL`).
- **`outcome`.** `handleSkip` records `studentAnswer: problem.answer, isCorrect: false, hadHelp: true` (`ActiveSession.tsx:1699-1707`); a judge would mark it right. A skip is `outcome: 'skipped', answer: null, isCorrect: false`. A blank worksheet answer is the same: today `session-converter.ts:66-67` stores `studentAnswer: parsed.studentAnswer ?? 0, isCorrect: false`, and `judge(0)` would be true when the answer is 0, so the converter emits `outcome: 'skipped', answer: null` (R16). `timeout` is for a presentation with a clock (none in this plan; flash anzan v1 has none); `isCorrect: false`, `answer: null`. **The legacy top-level projection is frozen with its quirks (K14, S4):** for `outcome: 'skipped'` and `'timeout'` the server writes `studentAnswer: problem.answer, isCorrect: false, hadHelp: true, helpTrigger: 'manual'` at top level exactly as `handleSkip` does today, whatever the body shape, so a K4 envelope skip and a K1 legacy skip are byte-identical at top level and every reader of `studentAnswer` (`DetailedProblemCard.tsx:642` "You said …", `AllProblemsSection.tsx:182, 190, 443`, `AttemptHistoryPanel`, `LiveResultsPanel`, which move to `TryCard` only in K5b, and every old bundle forever) shows what it shows today. New readers read `outcome`. Old rows: `outcome = 'answered'` always (a skipped row is wrong either way; its stored answer is the correct one, so `TryCard` shows "skipped" when `hadHelp && helpTrigger === 'manual' && answer === problem.answer && !isCorrect` as a display heuristic only, never for counting).
- **`payload`** is what a row needs, beyond its shared fields, to stand alone when the plan's content is slimmed or the kind is unknown to the image; it is never a second copy (R10). Arithmetic rows already carry their snapshot at top level (`problem`, `studentAnswer`, `skillsExercised`, `usedOnScreenAbacus`, `SlotResult :261-262`), and those fields keep being written on every arithmetic row, indefinitely (K14): they are what every open old bundle reads (`SessionProgressIndicator.tsx:203, 217, 231`; the normalizer's `resolveItemId :111-118`) and what `batchGetRecentSessionResults` filters on (`session-planner.ts:1284`). So arithmetic's stored `payload` is `{ kind: 'arithmetic' }` and the normalizer lifts `{ problem, usedOnScreenAbacus }` into the in-memory `payload` through arithmetic's `payloadOf`. A `GeneratedProblem` with its `generationTrace` is the bulk of a row (`:1232`, "10-50KB per session"), and `evidence-query.ts:186-217` and `:1234-1246` read `results` whole for every BKT computation; no phase copies the snapshot, so rows grow only by the envelope's own fields, about 200 B an arithmetic row from K1a (`itemId`, `outcome`, `answer`, `evidence`, `payload: { kind }`; 185–212 B measured), against the 10–50 KB a session's snapshots already take (amendment A2). A new kind stores its snapshot in `payload` once.
- **Parts.** Arithmetic parts keep `type, format, useAbacus, slots` at top level and gain `presentation` (= `type`). The report row gains `presentation` **beside** `type` (R3). Another kind's part is `{ kind, partNumber, presentation, estimatedMinutes, content }`. `partNumber` widens to `number` (`:32`; `SlotResult.partNumber :258`; `GeneratedProblem.partNumber :164`; `session-planner.ts:584, 694, 767, 950`; `offline-sessions/route.ts:72`; `session-converter.ts:16`; `arithmetic/state.ts:184`).
- **`part_states`** encoding is unchanged (K4). A kind on the general contract stores whatever its `State` is, as today (`partStateOf`, `session-plan-normalize.ts:229-234`).
- **`summary.composition`** (K6): the composer's trace, additive on the `summary` JSON. `summary.parts[]` gains `kind`, `presentation`, `key`, `label`, `emoji`, `itemCount`; `type`/`problemCount`/`description` keep being written for arithmetic (K14). `skippedParts[]` gains `kind`, `presentation`, `key`; `type` stays for arithmetic.
- **Preferences** (K6b): `player_session_preferences` JSON gains nothing new for the three keys; `partWeights` is typed `Record<string, number>` (today's three keys are a valid value), and `kindPreferences: Record<string, unknown>` is added for a kind's own settings (flash anzan's `perTermMs`), so a new kind or presentation adds no column and no key to any file outside its folder (R8).

##### A23.2 The reference

`GL-` + 4 characters from `23456789ABCDEFGHJKMNPQRSTVWXYZ` (no 0/1/I/L/O/U; 810 000 values), as drawn (`GL-7K2Q`). **Minted in the browser** (`crypto.getRandomValues`, `lib/glitch-ref.ts`), so it shows offline and is the same string on the note, the Why panel, the row and the report; the server validates `^GL-[23456789A-HJKMNP-TV-Z]{4}$` and stores it as sent. Uniqueness is per session (unique index `(session_plan_id, ref)`); the row's primary key is a cuid. A reference alone is not globally unique, so the MCP lookup returns every match newest first with its session and date (A23.3); across sessions a collision needs two glitches to draw the same 4 characters, and the session id on the Why panel's row disambiguates.

**How it reaches the server when nothing reaches the server.** The glitch write is an outbox entry like a try, queued behind the tries it is about, so it lands when they land and never before. Its reply flips the Why panel's footer from `Saving with this session's report…` to `Saved with this session's report.` (A23.8: the drawn footer claims "Saved" before anything was saved). A 404 from the glitch route (an R2 bundle on a pre-R1 server after a rollback) drops the entry, no retry, footer `Couldn't be saved. Copy the reference.`; the tries are unaffected.

##### A23.4 The outbox

`components/practice/session/outbox.ts` replaces `writeQueue.ts` (`createOutbox(send, { persist })`, kind-blind, fake-timer testable), owned by `PracticeClient` as the queue is today. Entries are tries (`first_or_retry`), do-overs and glitch writes, in submit order; the head is in flight alone, and the next entry is sent only after the head's reply. **That ordering is what makes the trust rule cheap:** a reply to try N means every earlier try is acknowledged, so every screen the server's reply produces (a transition, a break, a retry round's interlude, the summary) is reached with an empty outbox, and only "end early" (reachable from any screen) can run with entries pending (below).

| Timer | Where | What | Why it is not a race fix |
|---|---|---|---|
| **T1, 15 s fetch deadline** | `sendTryWrite`, an `AbortController` on each attempt's `fetch` (the `signal` option through `api()`; nothing else in `api()` changes) | A hung socket rejects as `timeout`; the row CAS's three attempts finish well inside it. | Without it the outbox has nothing to retry: a dead connection looks like a slow one forever. |
| **T2, 5 s pill deadline** | the outbox, one timer armed when an entry becomes head, cleared on its reply | Time since the head was *enqueued* > 5 s → `delayed: true` (the pill, G3; the hold line, G4). Not on the first failure: a blip resent at once stays invisible (G10). | A display threshold: when to tell the kid. Nothing waits on it. |
| **T3, backoff** | the outbox, after a retryable failure of the head | Delays `0, 1, 2, 4, 8, 16, 30, 30…` s between attempts (the first is today's immediate resend). Cut short by `online`, `visibilitychange` → visible, and **Send now**. Keeps running while paused (sending is not practising). | The retry policy for an approved outbox; the resend is safe because `recordTry` answers a duplicate `tryId` from the stored row before anything else (`record-try.ts:475`), so a landed-but-unanswered try is confirmed, never doubled. |

**Retryable:** a network error, T1, a 5xx, 503 `write_contention`, 409 `unknown_kind`. **Terminal:** every other 4xx (G5–G8); the head and the entries behind it are dropped, `onDropped(entry, error)` fires for the screen (resync and the note), and the glitch entry for it is enqueued. A terminal reply on a glitch entry drops that entry alone.

**Send now** aborts any attempt in flight, resets T3 and sends the head at once; the pill reads `Sending…` until the reply. If `navigator.onLine` is false it still sends (the flag is unreliable). While the outbox drains, each landed try's reply plan is applied to the cache as today (`onSuccess`), and the last plan wins.

**Practice continues** exactly where K5a-3a let it: a first-round try mid-part advances optimistically whatever the outbox holds; its feedback is the optimistic one, and its dot stays unlit until the server's plan shows the try. **A step the server decides holds** (G4): the shell's `await onAnswer` / `await onRecordRedo` / the skip's `await write` resolve only when that entry lands or is dropped; the feedback stays on screen, the hold line joins the pill at T2, and the next item loads from the reply's plan, as K5a-3a derives it. There is no bound on how far ahead a kid gets mid-part: the next part's end is the natural one.

**`round` (A16).** The outbox sends the round the screen showed. In order, a held first-round try reaches the server before the optimistic ones behind it, and a lost-reply resend is a duplicate, so the only `not_current` the outbox can meet is a screen that really was behind (another tab, the teacher's `control_session`, a plan the screen never received): G5, dropped with the entries behind it.

**Persistence.** The outbox is mirrored to `sessionStorage` (`abaci.outbox.<planId>`: the entries' request bodies, kind, `enqueuedAt`, `attempts`), rewritten on every change, deleted when empty. It survives a reload and dies with the tab. On mount, before the shell renders, `PracticeClient` drains a non-empty outbox for this plan in order (a terminal reply drops as above and records G5), applies the last reply's plan, then renders; a key for another plan is deleted. **Privacy:** the entries are the request bodies the server is about to store (ids, the answer digits, timings, a reference), no name, no free text, cleared on drain; `localStorage` is rejected because it outlives the tab and the sign-out on a shared device. Open question Q1.

**Interplay.** *Pause* (the kid's, the teacher's, the HUD's): T3 keeps running, Send now works. *The observer broadcast:* unchanged by the outbox (it carries the item on screen, not the write); on a G1/G2 correction the shell re-emits with the settled verdict (A23.5). *End early* with a non-empty outbox: the tap first drains with a short confirm (copy E1), `Wait` keeps draining with the pill, `End anyway` ends and loses the pending answers, said plainly; with an empty outbox, as today. *A do-over* goes through the outbox like a try; its return target comes from its reply (held, G4). *A skip* likewise.

##### A23.5 Reconciliation (A11)

The reply reaches the screen: `recordTryWrite` returns `{ plan, try }` (`RecordReply`), the mutations' `onSuccess` sets the plan as now, `handleAnswer` / `handleRecordRedo` resolve the reply (`null` for a dropped entry), `onAnswer`/`onRecordRedo` are typed `Promise<RecordReply | null>`, and the shell's `chooseAdvanceTarget`/`chooseRedoReturnTarget` read `reply.plan`. A `try: null` (a duplicate whose row was not found) settles nothing.

`decideFeedback` stays the one place the optimistic feedback is decided; **`settleFeedback(reply)`** beside it is the one place it is settled: `TryFeedback` gains `settled: null | { verdict, agreed: boolean, ref?: string }`. When the stored verdict agrees, nothing on screen changes. When it differs:

- **The verdict and the answer shown.** `feedback.verdict` becomes the stored one and `showAnswer` is recomputed from it with the same rule (`skipped || isCorrect || round >= kind.maxRounds`): G1 at round 0 with rounds left hides the answer (image 1 shows `4 ✕` and no answer); G2 shows it. Arithmetic's `ItemView` reads `feedback.verdict` (today it reads only `showAnswer`) for the ✓/✕ and the colours, and `PracticeFeedback` reads it too.
- **The pacing.** Awaited paths settle before the 500/1500 ms timer is armed, so they pace on the stored verdict. The optimistic path (`void onAnswer`) attaches `.then(settle)`: a reply that disagrees before the slide clears the timer and re-arms 1500 ms from the reply (a wrong try's pacing); a reply after the slide corrects nothing that is gone: the answered problem has slid off, the note stands under the problem now on screen, and `that one` in its copy refers back. Image 1's ✕ on the answered problem is what the kid sees in the first case only (A23.8).
- **The note.** The shell renders `GlitchNote` (`components/practice/session/GlitchNote.tsx`: the line, `Why?`, the `GlitchWhy` popover with the two sentences, `Ref GL-XXXX`, `Copy` through `navigator.clipboard.writeText` with a select-the-text fallback, the three-state footer) under the kind's view, kind-blind; the kind's view does not know. It clears on the next submit. The stale-screen line is the same component at the top placement.
- **What depended on the optimistic verdict.** *Retry membership and the dots:* nothing client-side holds them; `pendingRetries`, the interlude's count (`kind.roundSizeOf(plan)`) and the dots read the server's plan, which the reply already set. *The slide-off:* `ItemView.tsx:1003` renders `isCorrect={feedback?.verdict === 'correct'}` for the outgoing problem (G12, fixed: a wrong try slides off under "The answer was N" / "Not quite." per `showAnswer`, a right one under "Correct!"). *The broadcast:* the shell's broadcast effect reads `feedback.settled?.verdict ?? phase.result`, so the observer sees the correction; its own note is K5b's (Q3). *Vision training data* (`collectVisionTrainingData` in `ItemView.handleSubmit`, today on the optimistic ✓): moved behind the settled verdict (a sample labelled by a corrected verdict is a bad sample). *The assistance machine* (`assistance.onWrongAnswer` on the optimistic ✕): left as is, it is per item and the item is advancing. *The video marker* (`sendProblemMarkerRef` 'answer-submitted' with the optimistic `isCorrect`): left as is and named here; the glitch row names the try the marker names.
- **The record.** G1/G2 enqueue a `verdict_corrected` glitch entry with both verdicts, the answer, the item, both clocks and `slidBeforeReply`.

A mismatch between `kind.check` and `kind.judge` is, for arithmetic, the same pure function run twice, so a correction means a stale problem on screen, a different parse of the answer, or a bundle/server skew: a display bug, which is why the row carries both builds and the UA, and why the counter is the "zero in production" check. A kind without `check` (A11: none today; K8 may be one) has no optimistic verdict and settles on the reply, held as G4.

##### A23.8 Where the design is unbuildable or dishonest, and what this plan does instead

1. **"Saved with this session's report." before anything was saved** (image 3). The glitch row rides the same outbox as the tries; for G1/G2 it usually lands within a second, but for a panel opened during an outage the footer would lie. Three states, locked in A23.9: `Saving with this session's report…` → `Saved with this session's report.` → `Couldn't be saved. Copy the reference.` (the 404 case). Recommended; the owner approved the one string.
2. **Image 1's ✕ on the answered problem** can only be drawn when the reply beats the 500 ms slide. After the slide the answered problem is gone; the plan does not hold the slide for the reply (that would make every right answer wait for the server, which K5a-3a was built to avoid). The note's `that one` is written to refer back; the dot for the item turns from the server's plan.
3. **"Send now" during an attempt in flight** must do something or it is a lie: it aborts the attempt and sends again at once (safe by `tryId`).
4. **The pill counts "answers".** A pending skip or do-over is counted as an answer; `1 try not saved yet` is truer and worse for a kid. Kept as drawn.
5. **The hold** (a part's last item while a save hangs) has no drawing. Without a line the kid sees a frozen feedback; the pill is in the student row, far from a phone's eye. One line by the pattern (G4), no Why. Q2.
6. **The do-over refusal is mostly the screen's fault** (it offered a redo the server will refuse). The note is honest about it ("The screen shouldn't have offered it") and R2 stops offering it; the note then only fires on skew.
7. **A reload with answers pending** loses them unless the outbox persists. The plan persists in `sessionStorage` (A23.4) rather than record a loss it cannot send. Q1.
