# Practice kinds: plan of record (2026-11-27, rev. 3)

Companion to the [session architecture plan](../session-architecture/plan-of-record.md) (Phases 1–6 live on prod 2026-11-27, PRs #239–#275) and its [findings](../session-architecture/findings.md). That rework is the foundation: one flow machine owns the rhythm, every write is a CAS on `rowVersion`, one report serves every view, every try has an id, and a part is known to structure only through `PartKind`. This document settles how **many kinds of practice**, each in several **presentations**, plug into that session with no edit outside their own folder.

Paths are under `apps/web/src/`; `L/` is the ledger checkout (`~/projects/soroban-abacus-flashcards-practice/apps/web/`, read-only). Every code claim was re-read at `c12abd87f`. Rev. 2 answers [review 1](review-1.md) (R1–R19), rev. 3 [review 2](review-2.md) (S1–S11); §8 records each finding and what changed. The owner took every §7 recommendation on 2026-11-27; §7 is decisions now.

**The bar.** Adding a kind = one new folder plus one line in each of **three** registries: the shared core registry (`parts/registry.ts`: cursor, judge, presentations, evidence, describe; pure, read on both sides), the server-only planner registry (`parts/planner-registry.ts`: `loadContext`, `offer`, `plan`; S1) and the browser registry (`parts/browser-registry.ts`: views). Rev. 2 said two; the third line is the price of keeping database code out of the client bundle, said plainly (§8 S1). Adding a presentation of an existing kind = one folder plus one line in that kind's presentation list and one in its browser file. Every view (kid's screen, transition, summary, share link and OG, live observer, dashboard lists, adult review, MCP tools, song) handles it with no edit. Tests enforce this (§4 Phase K4). The rhythm `part, (break, part)*, end` then song and summary does not change.

**The rule behind the rule.** A kind that needs an edit outside its folder and its three registry lines is a defect in the architecture, not in the kind; the architecture is fixed first (an entry in §8, then a phase).

## 1. Target model

### 1.1 Taxonomy

| Term | Meaning | Today | Examples to come |
|---|---|---|---|
| **Kind** | What the items are and how the part's cursor moves. Today's behaviour, reproduced exactly: offers come in kind-registration order then the kind's own order (arithmetic: abacus, visualization, linear, as `part-gating.ts:44`); an offer is kept iff `enabled[key]` and `eligible`; `weight` normalized over kept offers (`session-planner.ts:550-553`); minutes = `budget × normalizedWeight`, where `budget = durationMinutes` under `breaks: 'outside'`; `plan()` derives `itemCount = overrideItemsPerPart ?? max(2, floor(minutes·60 / secondsPerItem))` from its own offer (`:594-598` today, arithmetic's pace; R8); no reorder. `maxParts: 3` keeps the break count at today's two (§7 Q2, decided).

**Over the cap: rotation (S5).** When more offers are on and eligible than `maxParts`, `selectOffers` keeps the `maxParts` **least recently practiced** and saves the rest for next time: never practiced sorts first, then oldest `lastPracticedAt`; ties (never-practiced together, or practiced in the same session) break by offer order (kind-registration order then the kind's own order, the same order that already decides part order). Weight is never a tie-break: the adult's weight means minutes, not priority. Kept offers keep their offer order and share the budget by weight as before. The host computes `LastPracticed` from the student's recent plans (`completedAt ?? startedAt` of the latest plan whose `parts[]` has a part with that key and at least one try in it; a pre-K6 part's key is its `type`); the composer is given it, not the DB. With three or fewer chips on, `selectOffers` keeps them all and the plan is today's (golden plan). The saved offers go to `skipped[]` with `reason: 'over-cap'`, so the summary's skipped-parts line reads "Visualize: saved for next time (3 parts per session)" through `skipped-parts.ts` with no new reader. **What the adult sees (K6b):** `/offers` returns the offers, `lastPracticedAt` per key and the policy; the modal runs the same pure `selectOffers` and, when any offer is over the cap, shows under the chips "Today: Abacus, Flash, Linear · Next time: Visualize"; an over-cap chip stays lit with a small "next time" badge, never greyed (it is on, and it will run). The order of "next time" is the rotation's. The tie-break and the rotation are pinned in `compose()`'s unit tests. `NoEligiblePartsError` when nothing is kept (`:546-548`). The trace is stored additively as `summary.composition` (the `summary` JSON column, `session-plans.ts:651`; there is no plan-level generation trace today, `GenerationTrace` is per problem, `:133-146`) and is what the ledger's `plan.decided` event will carry (`L/docs/...:96`).

Why breaks must be in the budget at all: the flow machine runs a break after **every** part transition when breaks are enabled (`session-flow.ts:226-255`), each up to `GameBreakSettings.maxDurationMinutes` (default 5, `session-plans.ts:466-470`); today `durationMinutes` is spent on practice only (`session-planner.ts:595`) and nothing in the planner or the time estimates counts a break minute, so a 12-minute three-part session is 12 + up to 10 minutes and the fixed shape is the only bound. Five parts would make that 12 + 20 (R5).

- **Rows** stay in `session_plans.results` (`session-plans.ts:696`); no column changes in any phase of this plan. New fields on each try are JSON (D8): `itemId`, `outcome`, `answer`, `evidence`, `payload`. `isCorrect` keeps its name and is the server's verdict from K1 on.
- **`evidence`** is `{ skills, presentation }` or `null`. The mode is `masteryModeOf(presentation)` at read time (K2): the kind's `presentations.get(id).masteryMode`, or, for an id no registry knows, the id itself (its own mode: recorded, not consulted). Absent (old rows) → the normalizer derives `{ skills: skillsExercised, presentation: part.type ?? 'linear' }`, reproducing `bktModeOf`'s legacy default (`arithmetic/server.ts:102`, `evidence-query.ts:154`). SQL tells null from absent with `json_type(value, '$.evidence')` (`'null'` vs `NULL`).
- **`outcome`.** `handleSkip` records `studentAnswer: problem.answer, isCorrect: false, hadHelp: true` (`ActiveSession.tsx:1699-1707`); a judge would mark it right. A skip is `outcome: 'skipped', answer: null, isCorrect: false`. A blank worksheet answer is the same: today `session-converter.ts:66-67` stores `studentAnswer: parsed.studentAnswer ?? 0, isCorrect: false`, and `judge(0)` would be true when the answer is 0, so the converter emits `outcome: 'skipped', answer: null` (R16). `timeout` is for a presentation with a clock (none in this plan; flash anzan v1 has none); `isCorrect: false`, `answer: null`. **The legacy top-level projection is frozen with its quirks (K14, S4):** for `outcome: 'skipped'` and `'timeout'` the server writes `studentAnswer: problem.answer, isCorrect: false, hadHelp: true, helpTrigger: 'manual'` at top level exactly as `handleSkip` does today, whatever the body shape, so a K4 envelope skip and a K1 legacy skip are byte-identical at top level and every reader of `studentAnswer` (`DetailedProblemCard.tsx:642` "You said …", `AllProblemsSection.tsx:182, 190, 443`, `AttemptHistoryPanel`, `LiveResultsPanel`, which move to `TryCard` only in K5b, and every old bundle forever) shows what it shows today. New readers read `outcome`. Old rows: `outcome = 'answered'` always (a skipped row is wrong either way; its stored answer is the correct one, so `TryCard` shows "skipped" when `hadHelp && helpTrigger === 'manual' && answer === problem.answer && !isCorrect` as a display heuristic only, never for counting).
- **`payload`** is what a row needs, beyond its shared fields, to stand alone when the plan's content is slimmed or the kind is unknown to the image; it is never a second copy (R10). Arithmetic rows already carry their snapshot at top level (`problem`, `studentAnswer`, `skillsExercised`, `usedOnScreenAbacus`, `SlotResult :261-262`), and those fields keep being written on every arithmetic row, indefinitely (K14): they are what every open old bundle reads (`SessionProgressIndicator.tsx:203, 217, 231`; the normalizer's `resolveItemId :111-118`) and what `batchGetRecentSessionResults` filters on (`session-planner.ts:1284`). So arithmetic's stored `payload` is `{ kind: 'arithmetic' }` and the normalizer lifts `{ problem, usedOnScreenAbacus }` into the in-memory `payload` through arithmetic's `payloadOf`. A `GeneratedProblem` with its `generationTrace` is the bulk of a row (`:1232`, "10-50KB per session"), and `evidence-query.ts:186-217` and `:1234-1246` read `results` whole for every BKT computation; no phase copies the snapshot, so rows grow only by the envelope's own fields, about 200 B an arithmetic row from K1a (`itemId`, `outcome`, `answer`, `evidence`, `payload: { kind }`; 185–212 B measured), against the 10–50 KB a session's snapshots already take (amendment A2). A new kind stores its snapshot in `payload` once.
- **Parts.** Arithmetic parts keep `type, format, useAbacus, slots` at top level and gain `presentation` (= `type`). The report row gains `presentation` **beside** `type` (R3). Another kind's part is `{ kind, partNumber, presentation, estimatedMinutes, content }`. `partNumber` widens to `number` (`:32`; `SlotResult.partNumber :258`; `GeneratedProblem.partNumber :164`; `session-planner.ts:584, 694, 767, 950`; `offline-sessions/route.ts:72`; `session-converter.ts:16`; `arithmetic/state.ts:184`).
- **`part_states`** encoding is unchanged (K4). A kind on the general contract stores whatever its `State` is, as today (`partStateOf`, `session-plan-normalize.ts:229-234`).
- **`summary.composition`** (K6): the composer's trace, additive on the `summary` JSON. `summary.parts[]` gains `kind`, `presentation`, `key`, `label`, `emoji`, `itemCount`; `type`/`problemCount`/`description` keep being written for arithmetic (K14). `skippedParts[]` gains `kind`, `presentation`, `key`; `type` stays for arithmetic.
- **Preferences** (K6b): `player_session_preferences` JSON gains nothing new for the three keys; `partWeights` is typed `Record<string, number>` (today's three keys are a valid value), and `kindPreferences: Record<string, unknown>` is added for a kind's own settings (flash anzan's `perTermMs`), so a new kind or presentation adds no column and no key to any file outside its folder (R8).
